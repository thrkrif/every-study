# ADR-0005: 채팅·알림·스케줄러

- 상태: 확정 (2026-11-13)
- 일자: 2026-11-11
- 관련: [ARCHITECTURE 4.6~4.8](../ARCHITECTURE.md), PRD 4.5, 4.6, 4.12, 8장

## 배경

채팅(실시간), 알림(신뢰성 요구), 시간 기반 처리(노쇼 판정, 일정 알림)는 모두 "서버가 시각에 맞춰 일을 하거나 밀어 주는" 문제다. 초기 규모는 서버 1대이며 Redis는 두지 않기로 했다.

## 결정

### 채팅
- WebSocket + STOMP, 시작은 **단일 서버 내장 브로커**.
- 메시지는 **DB에 먼저 저장하고** 전달한다. 이전 대화는 커서 기반 페이징으로 조회한다.
- 구독과 전송마다 서버가 **참여 여부를 검사**한다. 나가기 시 구독을 끊는다 (강퇴 기능은 없다).
- **스터디 종료 시 채팅방을 폐쇄**하고(전체 구독 종료, 전송 거부), 메시지는 보관 기간(PRD 4.14)이 지나면 스케줄러가 영구 삭제한다. 종료 경계는 한국 시간 자정이다.
- 인증은 핸드셰이크 쿠키 (ADR-0002).
- **서버 증설 시**: Spring STOMP 브로커 릴레이는 STOMP를 지원하는 외부 브로커(RabbitMQ, ActiveMQ)에 연결한다. PRD 4.12가 말한 "Redis pub/sub"은 STOMP 브로커가 아니므로 그대로는 연결되지 않고 별도 브리지 구현이 필요하다. 증설 시점에 **RabbitMQ 릴레이를 우선 검토**한다 (PRD 4.12 문구는 v0.4에서 이미 맞췄다).

### 알림
- 비즈니스 트랜잭션 안에서 `notification_outbox`에 기록하고, **워커가 발송**한다 (트랜잭션 아웃박스). 발송 실패는 백오프로 재시도하고 최대 횟수 후 실패 상태로 남긴다.
- 일정 알림(전날, 1시간 전, 체크인 오픈)은 스터디 개설 시 **예정 발송 시각으로 미리 기록**하고, 취소 시 취소한다. 모든 알림 건은 유효 기한을 가져, 서버 중단으로 기한이 지난 건은 보내지 않는다.
- 대기 알림(PRD 4.14)도 같은 아웃박스를 쓴다. 정원 변경·자리 발생 이벤트마다 자격이 남은 대기자(알림 시점에 재검사, PLAN X-20)에게 건별로 만들어 워커가 분산 발송하고, 신청 경쟁은 ADR-0004의 락과 정원 검사가 정리한다.
- 채널은 웹 푸시(VAPID)와 이메일. 수신 설정은 **발송 시점**에 확인한다.
- 푸시 서비스가 만료·삭제로 응답한 구독은 정리한다.

### 스케줄러
- 서버 1대에서는 Spring `@Scheduled`. 기억은 **DB가** 한다: "시각이 지났고 아직 처리되지 않은 건"을 조회해 처리한다. 메모리 타이머로 미래 작업을 예약하지 않는다.
- 모든 작업은 **멱등**이고, 한 번에 처리하는 건수에 상한을 둔다.
- 작업: 알림 워커, 노쇼 후보 판정, 이의 기간 경과 확정, 주최자 미도착 세션 무효 처리, 스터디 종료 처리, 채팅 메시지 보관 만료 삭제, 만료된 리프레시 토큰 정리.
- 서버를 2대 이상으로 늘릴 때 분산 락(ShedLock 등)을 도입한다.

## 대안

- **Redis pub/sub으로 채팅 확장**: 위 이유로 직접 구현 부담이 커서 기각(증설 시 재검토).
- **Quartz 등 영속 스케줄러**: 현재 요구는 "지난 건 조회" 방식으로 충분해 기각.
- **알림 즉시 동기 발송**: 외부 장애가 비즈니스 트랜잭션에 번져 기각.

## 결과와 영향

- 알림은 최소 한 번 발송되며, 드물게 중복될 수 있어 알림 내용은 중복을 견디게 쓴다.
- 서버가 멈췄다 켜져도 밀린 작업이 이어서 처리된다.
- 서버 시각이 정확해야 한다 (NTP). 모든 시간 로직은 주입된 `Clock`을 쓴다.
- iOS Safari 웹 푸시는 홈 화면에 추가한 PWA에서만 동작하므로, 출시 전 실기기 검증이 필요하다 (PRD 9장).
