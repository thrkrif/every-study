# ADR-0004: 정원·승계 동시성과 정합성

- 상태: 확정 (2026-11-13, 방향은 ADR-0001의 "스터디 행 락"을 구체화)
- 일자: 2026-11-11
- 관련: [ARCHITECTURE 4.2~4.5](../ARCHITECTURE.md), PRD 4.4, 4.13, 8장

## 배경

PRD는 두 가지 정합성을 요구한다. (1) 마지막 1자리에 동시 신청이 와도 정원을 넘기지 않는다. (2) 주최자 나가기와 참여자 나가기가 겹쳐도 승계 대상이 한 명으로만 정해진다. MySQL 기본 격리 수준은 `REPEATABLE READ`라 범위 조건 락은 갭 락을 만든다.

## 결정

1. **스터디 단위 직렬화**: 멤버 구성을 바꾸는 모든 작업(신청, 취소, 채팅방 나가기, 정원 변경, 승계, 스터디 종료·파투 처리, 체크인·일회용 코드 체크인, 세션 무효·노쇼 후보 자동 판정)은 먼저 `study` 행을 `SELECT … FOR UPDATE`(JPA `PESSIMISTIC_WRITE`)로 잠근다. 같은 스터디의 작업은 순서대로 실행된다.
2. **락 안에서 모든 검사**: 정원, 이용 제한, 입장 기준, 중복 확인을 한 트랜잭션에서 한다. 락을 잡기 전에 읽은 값으로 판단하지 않는다. 이 트랜잭션들은 격리 수준을 `READ COMMITTED`로 둔다. `REPEATABLE READ`에서는 트랜잭션의 첫 조회 때 읽기 시점이 고정되므로, 락 전에 한 번이라도 조회하면 락을 기다리는 동안 앞 트랜잭션이 커밋한 참여 행이 보이지 않는다 (PLAN T-016의 동시성 테스트가 정원 초과로 잡아냈다). `READ COMMITTED`에서는 잠그지 않는 조회도 락을 잡은 뒤에는 앞 트랜잭션이 커밋한 값을 본다.
3. **DB 제약을 이중 방어선으로**: `study_member (study_id, user_id)` 유일 제약. 현재 참여자 수는 `ACTIVE` 행을 락 안에서 센다 (카운터 컬럼을 두지 않아 어긋날 일이 없다. 병목이 되면 그때 카운터를 둔다).
4. **승계는 같은 락 안에서**: 남은 `ACTIVE` 참여자 중 서버가 무작위로 한 명을 고르고 `study.host_id`를 바꾼다. 승계 이력과 감점 이벤트도 같은 트랜잭션에 기록한다.
5. **락 순서 규칙**: 여러 행을 잠글 때는 `study` → `study_member` 순서로만 잠근다 (교착 방지). 락 대기 시간 제한을 두고, 초과하면 재시도 가능한 오류로 응답한다.
6. **멱등성**: 체크인은 `(study_id, user_id)` 유일 제약, 알림 발송은 건별 상태로 중복을 막는다. 스케줄러 작업은 모두 재실행해도 결과가 같게 만든다.
7. **이벤트 불변**: `attendance_event`, `host_penalty_event`는 추가만 한다. 정정은 새 이벤트로 한다. 집계는 이벤트에서 다시 만들 수 있어야 한다.

## 대안

- **낙관적 락(버전 컬럼)**: 마지막 자리 경쟁에서 재시도가 몰리고, 정원 같은 집합 조건에는 부적합해 기각.
- **카운터 컬럼 원자 증가**: 빠르지만 승계·취소와 맞물리면 불일치 위험이 있어 기각 (필요해질 때 재검토).
- **분산 락(Redis)**: 서버 1대에서는 불필요한 구성 요소라 기각.

## 결과와 영향

- 한 스터디에 요청이 몰려도 정확하다. 서로 다른 스터디는 서로 막지 않는다.
- 인기 스터디의 신청이 몰리면 대기가 생길 수 있다. 정원은 작아 트랜잭션이 짧으므로 소규모에서는 문제가 되지 않는다.
- **테스트 필수**: Testcontainers MySQL에서 (a) 마지막 1자리 N명 동시 신청, (b) 주최자 나가기와 참여자 나가기 동시 실행, (c) 같은 사용자의 중복 신청 동시 실행.
