# ADR-0002: 인증 — 소셜 로그인과 JWT 쿠키

- 상태: 확정 (2026-11-13)
- 일자: 2026-11-11
- 관련: [ARCHITECTURE 4.1](../ARCHITECTURE.md), [ADR-0001](0001-tech-stack.md), PRD 4.1

## 배경

로그인은 카카오·구글 소셜 로그인으로 확정이고, 토큰은 JWT를 httpOnly 쿠키로 보관하기로 했다 (ADR-0001).
쿠키를 쓰면 CSRF와 CORS 대응이 필요하고, 채팅(WebSocket)도 같은 인증을 써야 한다.

## 결정

1. **소셜 로그인은 서버가 처리한다.** Spring Security OAuth2 로그인으로 카카오·구글 인증을 받고, 성공 핸들러에서 **자체 토큰을 발급**한다. 소셜 토큰은 저장하지 않는다. 사용자 식별은 `(provider, 소셜 사용자 ID)`로 한다.
2. **토큰 2종, 모두 `HttpOnly; Secure` 쿠키.**
   - 액세스: JWT, 짧은 수명. 서명 키는 환경변수로 주입한다.
   - 리프레시: 불투명 랜덤 값. DB에는 **해시만 저장**하고, 사용할 때마다 **회전**한다. 재사용이 감지되면 해당 계열 전체를 폐기한다. 쿠키 `Path`를 갱신 엔드포인트로 제한한다.
3. **CSRF**: 이중 제출 쿠키 방식 (Spring Security의 SPA용 설정). 읽을 수 있는 CSRF 쿠키와 요청 헤더를 비교한다. 로그인·로그아웃 직후에는 새 CSRF 토큰을 받는다. `SameSite=Lax`와 `Origin` 검사를 함께 쓴다.
4. **같은 사이트 배포**: 프론트와 API를 같은 등록 도메인 아래(`app.*`, `api.*`)에 둬서 쿠키를 first-party로 유지한다. CORS는 프론트 오리진 하나만 허용하고 자격 증명을 포함한다.
5. **WebSocket**: 핸드셰이크 요청의 쿠키로 인증하고 `Origin`을 허용 목록으로 검사한다. 이후 STOMP 메시지는 그 사용자 주체로 처리된다 (STOMP 헤더의 계정 정보는 쓰지 않는다).
6. **로그아웃·탈퇴**: 리프레시 폐기 + 쿠키 삭제. 탈퇴는 소셜 식별값 삭제(PRD 4.1)와 함께 모든 리프레시를 폐기한다.
7. **권한**: 역할은 `USER`, `ADMIN`. 주최자 여부는 역할이 아니라 스터디 단위 관계(`study.host_id`)로 판정한다.

## 확정 값

| 항목 | 값 |
|---|---|
| 액세스 수명 | 15분 |
| 리프레시 수명 | 14일 (슬라이딩 아님, 회전 시 갱신) |
| 쿠키 | 프론트·API를 같은 사이트로 배포, `SameSite=Lax`. `Domain` 값은 도메인이 정해질 때 설정 |

## 결과와 영향

- 장점: 토큰이 JS에서 읽히지 않아 XSS 영향이 줄고, 폐기·강제 로그아웃이 가능하다.
- 비용: CSRF 처리와 리프레시 회전 구현이 필요하다. 프론트는 갱신 실패 시 로그인으로 보내는 공통 처리를 둔다.
- 로컬 개발은 `localhost`에서 같은 사이트로 동작하게 맞춘다 (HTTPS 전용 속성은 로컬 프로필에서만 완화).
- 구현 전에 Spring Security 최신 문서로 OAuth2 로그인·CSRF SPA 설정을 다시 확인한다.

## 후속 결정 (2026-11-17, T-004)

소셜 로그인과 토큰 쿠키 발급을 구현하며 아래를 정했다. 쿠키 이름·경로와 리다이렉트 대상의 현재 값은 [API 2장](../API.md)이 원본이고, 여기는 결정과 이유의 기록이다.

- **액세스 JWT는 HS256(대칭 키)으로 서명한다.** 발급과 검증을 같은 서버가 하므로(모듈러 모놀리스, ADR-0003) 키 쌍이 필요 없다. 키는 환경변수로만 받고 32자 미만이면 기동하지 않는다. 클레임은 `sub`(회원 ID), `role`, `iat`, `exp`뿐이고 이메일 같은 개인정보는 넣지 않는다. 버린 대안: RS256 → 검증만 하는 다른 서비스가 생기기 전에는 키 관리만 늘어 기각.
- **리프레시 쿠키의 `Path`는 `/api/v1/auth`다.** 위 결정 2의 "갱신 엔드포인트로 제한"을 그대로 따르면 로그아웃(`/api/v1/auth/logout`)이 폐기할 리프레시 토큰을 받지 못한다. 갱신과 로그아웃을 묶는 가장 좁은 경로로 둔다.
- **이메일은 공급자가 확인한 것만 저장한다** (PLAN D-9). 구글은 `email_verified`, 카카오는 `is_email_valid`·`is_email_verified`가 참일 때만이다. 카카오 이메일은 선택 동의라 없을 수 있고, 그때는 이메일 없이 가입된다. 확인되지 않은 주소는 남의 것일 수 있어 알림을 보내면 안 된다.
- **구글은 `openid` 범위 없이 사용자 정보 조회만 한다.** 필요한 것이 식별값(`sub`)과 이메일뿐이라 ID 토큰 검증 단계를 두지 않았다. 두 공급자가 같은 경로(인가 코드 → 사용자 정보 조회)를 타서 테스트의 가짜 구현도 하나다.
- **소셜 토큰은 메모리에도 두지 않는다.** Spring Security 기본값은 로그인한 사용자의 소셜 액세스 토큰을 서버 메모리에 보관한다. 결정 1(소셜 토큰 미저장)에 맞춰 보관소를 아무것도 저장하지 않는 구현으로 바꿨다.
- **서버 세션은 인가 요청(`state`)을 콜백까지 들고 있는 데만 쓴다.** 로그인 성공·실패 직후 세션을 없애고, 인증 상태는 세션에 저장하지 않는다(`STATELESS`).
- **온보딩 전 회원**은 닉네임·직군·지역이 `NULL`인 행으로 만든다 (DATA-MODEL 3장). 로그인 뒤 온보딩 화면으로 보내는 기준은 "신규"가 아니라 "온보딩을 마치지 않음"이다(가입 직후 창을 닫은 회원도 다시 온보딩으로 간다).
- **남은 것 (T-005)**: 쿠키의 액세스 토큰으로 요청을 인증하는 것, 경로별 권한, CSRF·CORS·`Origin` 검사, 갱신·로그아웃. 그때까지는 보호할 API가 없어 모든 요청을 허용한다.
- **알려진 한계**: 같은 소셜 계정의 첫 로그인 두 건이 동시에 오면 하나는 `UNIQUE (provider, provider_user_id)`에 걸려 실패한다(회원은 하나만 만들어진다). 다시 로그인하면 된다.
