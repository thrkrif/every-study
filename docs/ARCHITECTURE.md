# ARCHITECTURE — 모두의 스터디

- 상태·버전·근거 문서는 머리말을 따른다. 본문의 "제안"은 검토 후 확정, "확정"은 이미 결정된 사항이다.
- **정책 수치(시간·반경·점수 등)는 [PRD](PRD.md)가 원본**이며 이 문서는 값을 복사하지 않는다.
- 관련: [PRD](PRD.md) · [ADR-0001 기술 스택](adr/0001-tech-stack.md) · ADR-0002~0005 (12장)
- 이 문서는 **구조와 원칙**을 다룬다. 테이블·API 상세는 다음 단계(데이터·API 명세)에서 정한다.

## 1. 목표와 제약

| 우선순위 | 품질 속성 | 의미 |
|---|---|---|
| 1 | **정합성** | 정원 초과 확정, 주최자 이중 승계, 지표 오계산이 없어야 한다 (PRD 8장) |
| 2 | **감사 가능성** | 출석·점수·제재의 변동은 이벤트로 남기고 재계산할 수 있어야 한다 |
| 3 | **단순함** | 초기 규모는 소규모(수원 4개 구, 서버 1대, 확정). 분산 구성은 필요해질 때 도입한다 |
| 4 | **변경 용이성** | 정책 수치(시간창, 임계값, 감점)는 코드가 아닌 설정이다 |

비목표(MVP): 다중 서버, 마이크로서비스, 비대면 스터디, 추천 알고리즘, 결제.

## 2. 시스템 개요

```
 [브라우저: 모바일 웹/PWA]  ── Next.js (프론트, TypeScript)
        │ HTTPS (REST + WebSocket/STOMP, httpOnly 쿠키)
        ▼
 [Spring Boot 백엔드: 모듈러 모놀리스 1개]  ── 스케줄러·알림 워커 포함 (같은 프로세스)
        │                    │
        ▼                    ├─ 카카오/구글 OAuth2 (로그인)
   [MySQL 8]                 ├─ 웹 푸시 (VAPID) · 이메일(SMTP)
 (Flyway, utf8mb4)           └─ (브라우저가 직접) 카카오맵 JS SDK · 장소 검색
```

- 프론트와 백엔드는 **별도 배포 단위**다 (PRD 확정). 백엔드 API는 앱 확장을 고려해 프론트에 종속되지 않게 둔다.
- 카카오맵은 브라우저에서 호출하고, 서버는 **좌표와 장소명만 저장**한다. 서버가 지도 API를 호출할 필요가 없다.
- 상태는 DB에만 둔다. 서버 메모리에 비즈니스 상태를 두지 않는다 (재시작·증설 대비).

## 3. 백엔드 구조 (확정, ADR-0003)

**모듈러 모놀리스, 기능별 패키지.** 하나의 배포 단위 안에서 모듈 경계만 엄격히 지킨다.

| 모듈 | 책임 | PRD |
|---|---|---|
| `auth` | 소셜 로그인, 토큰 발급·갱신·폐기 | 4.1 |
| `user` | 프로필(닉네임·직군·지역), 탈퇴·익명화 | 4.1, 4.10 |
| `study` | 스터디·희망 직군·입장 기준, 일정(날짜·시작·진행 시간)·장소 수정, 참여 신청·취소(정원), 정원 변경, 주최자 승계, 상태·종료, 대기 신청 | 4.2~4.4, 4.13A, 4.14 |
| `attendance` | 체크인, 일회용 코드, 자동 판정(세션 무효, 노쇼 후보) | 4.6 |
| `trust` | 출석 이벤트 기록(다른 모듈은 공개 서비스로 기록을 요청), 출석률 집계, 참여자·주최자 제재, 이의 신청 | 4.7~4.9, 4.13B~D |
| `notification` | 알림 생성·발송(푸시/이메일), 수신 설정 | 4.5 |
| `chat` | 채팅방·메시지·읽음·공지·신고/차단, 스터디 종료 시 폐쇄와 메시지 삭제 | 4.12, 4.14 |
| `admin` | 이의·신고 큐, 신고 조치(스터디 강제 종료, 메시지 삭제, 이용 정지), 제재 해제 (간단한 어드민) | 4.11 |
| `meta` | 클라이언트용 코드 목록과 설정값(`GET /meta/options`). 다른 모듈의 설정 객체를 읽기만 하고, 다른 모듈은 `meta`를 참조하지 않는다 | 4.1~4.3 |
| `common` | 시간(`Clock`), 예외·오류 응답, 설정 속성, 로그 마스킹, 요청 추적(traceId), 감사 로그 기록(여러 모듈이 기록하므로 `admin`이 아니라 여기에 둔다). 기능 모듈과 달리 `web/service/domain/repository`로 나누지 않고 역할별 하위 패키지(`time`, `error`, `logging`, `web`, `security`, `code`)를 둔다. `security`에는 모든 모듈의 컨트롤러가 받는 로그인 회원 주체(`LoginUser`)가, `code`에는 여러 모듈이 함께 쓰는 고정 목록(직군·지역·주제, DATA-MODEL 1장)과 그 검증 애너테이션이 있다 | |

**패키지와 의존 방향 규칙**
- 패키지 모양은 `com.everystudy.<모듈>.<계층>`이고 계층은 `web`, `service`, `domain`, `repository`, `event`다. `event`에는 다른 모듈이 받는 도메인 이벤트 클래스를 둔다.
- 모듈 내부 계층: `web → service → (domain, repository)`. `web`은 같은 모듈의 `domain` 타입(enum 등)을 쓸 수 있지만 `repository`는 직접 쓰지 않는다. `service`는 `web`에, `domain`·`repository`는 `web`·`service`에 의존하지 않는다. 엔티티를 응답으로 그대로 내보내지 않는다(코드 리뷰로 확인).
- 모듈이 다른 모듈에 공개하는 것은 **`service`와 `event` 패키지뿐**이다. 다른 모듈의 `domain`·`repository`·`web`은 참조하지 않는다.
- `common`은 어느 모듈에서나 쓸 수 있고, `common`은 기능 모듈에 의존하지 않는다.
- 의존이 순환하지 않는다. 방향: `study/attendance → trust`, `* → notification`(공개 서비스 호출), `chat → study`(참여 여부 조회, 이벤트 수신). **`study`는 `chat`을 참조하지 않는다.**
- 모듈 간 결합은 **도메인 이벤트**로 푼다. 이벤트를 받는 방식은 결과가 함께 커밋돼야 하는지로 나눈다.
  - **같은 트랜잭션(동기 리스너)**: 비즈니스 변경과 함께 커밋되거나 함께 롤백돼야 하는 반응. `chat`은 `StudyCreated`·`StudyEnded`·`StudyCancelled`를 동기 리스너로 받아 채팅방을 만들고 닫는다.
  - **`AFTER_COMMIT`**: 유실돼도 되는 반응에만 쓴다 (STOMP 전달, 구독 종료). 커밋 뒤에 실패하면 되돌릴 수 없기 때문이다.
  - **알림**은 유실되면 안 되므로 `AFTER_COMMIT`에서 만들지 않는다. 변경을 일으킨 모듈이 같은 트랜잭션에서 `notification` 공개 서비스를 호출해 아웃박스에 기록한다 (4.6).
- 루트 패키지명은 **`com.everystudy`**(임시, 확정). 도메인이 정해지면 IDE 리팩터링으로 바꾼다.
- 위 규칙은 아키텍처 테스트(ArchUnit, `backend/src/test/java/com/everystudy/architecture/`)가 `./gradlew test`에서 검사한다. 규칙을 바꾸면 이 절과 테스트를 함께 고친다.

## 4. 핵심 설계

### 4.1 인증 (제안, ADR-0002)
- 카카오·구글 OAuth2 로그인 → 성공 시 **자체 토큰을 발급**해 쿠키로 내려준다. 소셜 토큰은 보관하지 않는다.
- 액세스 토큰(JWT, 짧은 수명)과 리프레시 토큰(불투명 값, DB에 **해시로 저장**, 회전)을 모두 `HttpOnly; Secure` 쿠키로 둔다.
- 상태 변경 요청은 CSRF 토큰(이중 제출 쿠키 방식)과 `Origin` 검사로 보호한다. 프론트·백엔드는 **같은 사이트(same-site)** 로 배포한다.
- WebSocket도 같은 쿠키로 핸드셰이크에서 인증한다.

### 4.2 정원 동시성 (확정 방향, ADR-0004)
- 참여 신청·취소·승계 등 **스터디의 멤버 구성을 바꾸는 모든 작업은 `study` 행을 `SELECT … FOR UPDATE`로 잠근 뒤** 수행한다. 한 스터디의 멤버 변경은 직렬화된다.
- 정원 검사, 중복 신청 검사(`study_member`에 `(study_id, user_id)` 유일 제약 + 상태), 입장 기준 검사를 같은 트랜잭션에서 한다. 검증 순서는 PRD 4.4 그대로: 스터디 상태(진행 중) → 정원 → 이용 제한 → 입장 기준 → 중복.
- MySQL `REPEATABLE READ`의 갭 락을 피하려고 범위 조건 대신 **부모 행 하나를 잠그는** 방식을 쓴다.
- 참여는 **승인 단계가 없다**. 참여 상태는 `ACTIVE`(참여 중) / `LEFT`(취소·나감) 정도로 단순하다.
- `study`의 저장 상태는 `ACTIVE` / `ENDED` / `CANCELLED` 세 가지다 (PRD 4.14). "모집 중·마감"은 정원 여유로 **계산하는 파생 값**이며 저장하지 않는다. 주최자에게 모집 마감 스위치가 없으므로 이 값을 직접 바꾸는 경로가 없다.
- **정원 변경(증액·감소)도 같은 `study` 행 락** 안에서 한다. 감소는 현재 `ACTIVE` 참여자 수 미만으로 못 내린다.
- 자리가 생기거나(참여자 나감) 정원이 늘면 대기 중인 사용자에게 보낼 알림을 같은 트랜잭션에서 아웃박스에 기록한다 (3장, 4.6. 자동 참여는 없고 신청은 선착순이라 위 락과 정원 검사가 그대로 경쟁을 정리한다).

### 4.3 주최자 승계 (확정 방향, ADR-0004)
- 주최자가 채팅방을 나가는 요청도 **같은 `study` 행 락** 안에서 처리한다. 남은 참여자 집합이 락으로 고정되므로, 참여자 나가기와 겹쳐도 승계 대상은 한 명으로만 정해진다.
- 처리(세션 시작 전까지만. 시작 후에는 승계하지 않음): 남은 `ACTIVE` 참여자가 없으면 스터디를 파투(취소), 있으면 **무작위 1명**을 새 주최자로 지정(수락/거절 없음). 같은 트랜잭션에서 `study.host_id` 변경, 승계 이력, 전 주최자 감점(PRD 4.13B 조건일 때) 이벤트를 기록한다.
- 무작위 추첨은 서버에서 한다 (테스트에서는 주입 가능한 `RandomSource`로 고정).

### 4.4 체크인과 출석 판정 (제안)
- **판정은 서버가 한다.** 클라이언트가 보낸 위치(위도·경도·정확도)와 **서버 시각**만 신뢰한다.
- 거리 계산은 서버에서 Haversine으로 한다 (반경은 설정값, 값은 PRD 4.6). MySQL 공간 함수는 쓰지 않는다 (ADR-0001).
- 일회용 코드: 주최자 체크인이 **성공한 뒤에만** 발급, 스터디(세션) 단위, 짧은 수명, 입력 횟수 제한. 위치 권한 거부·GPS 실패 시 유일한 대체 수단 (PRD v0.3).
- 체크인 요청은 `(study_id, user_id)` 유일 제약으로 **멱등**하게 처리한다 (중복 탭·재시도 대비).
- **집계 대상**: 신청은 체크인 오픈 전까지만 받으므로(PRD 4.6) 출석 판정 대상은 `ACTIVE` 참여자 전원이다. 신청·대기 마감은 락 안에서 서버 시각으로 검사한다.
- 자동 판정(스케줄러, 4.7): 체크인 마감 시각(PRD 4.6) 이후 `미체크인`을 `노쇼 후보`로 바꾸고 통지, 이의 기간(PRD 4.9) 경과 후 확정. 주최자가 체크인 마감까지 체크인하지 않으면 세션 `무효`.
- 위치 값은 **판정에 필요한 최소값(거리·정확도·방식)만 저장**하고 원본 좌표는 저장하지 않는 것을 제안한다 (PRD 8장 "저장 최소화").

### 4.5 출석 지표와 제재 (제안)
- **이벤트 로그 + 집계 캐시** 구조다 (PRD 4.7 "정책 변경 시 재계산").
  - `attendance_event`: 출석/지각/노쇼/직전취소/세션무효 등 사실 기록 (추가만, 수정 없음. 이의 인정 시 정정 이벤트를 추가).
  - `user_trust_summary`: 최근 N회 출석률·횟수 캐시. 이벤트가 쌓일 때 갱신하고, 설정이 바뀌면 전체 재계산 배치로 다시 만든다.
- 주최자 점수는 `host_penalty_event`(점수·사유·발생 시각)로 기록하고, **롤링 기간(PRD 4.13B) 합계는 조회 시 계산**한다 (소멸 배치가 필요 없다).
- 제재(참여자 제한·정지, 주최자 개설 제한)는 `user_sanction`(종류·시작·종료·사유)으로 저장하고, **신청·개설 시점에 현재 유효 여부를 검사**한다.
- 이의 신청이 인정되면 해당 이벤트를 정정하고 집계를 재계산한다. 모든 수동 변경은 감사 로그(누가·언제·무엇을)에 남긴다.

### 4.6 알림 (제안, ADR-0005)
- 서비스 코드는 알림을 **직접 보내지 않고** `notification_outbox`에 같은 트랜잭션으로 기록한다 (트랜잭션 아웃박스). 비즈니스 변경과 알림 생성이 함께 커밋되거나 함께 롤백된다.
- 워커(스케줄러)가 대기 건을 읽어 푸시/이메일로 발송하고, 실패하면 **재시도(백오프, 최대 횟수)**, 끝내 실패하면 실패 상태로 남긴다 (PRD 8장 신뢰성).
- 채널별 수신 설정을 발송 시점에 확인한다. 웹 푸시는 VAPID, 구독 정보는 사용자별 저장. iOS Safari는 홈 화면에 추가한 PWA에서만 푸시가 동작하므로 출시 전 실기기 검증이 필요하다 (PRD 9장).
- 일정 알림(전날·1시간 전·체크인 오픈)은 스터디 개설 시 **예정 발송 건으로 미리 기록**하고, 스터디가 취소되면 해당 건을 취소한다 (참여자가 생기면 일정이 바뀌지 않으므로, 주최자 혼자일 때의 일정 수정에만 건을 다시 만든다). 모든 알림 건은 **유효 기한(`expires_at`)**을 가지며, 서버 중단 등으로 기한이 지난 건은 발송하지 않고 취소 처리한다 (예: 모임 시작 후의 체크인 오픈 알림). 개설 시점이 이미 전날·1시간 전을 지났으면 그 건은 만들지 않는다.

### 4.7 스케줄러 (제안, ADR-0005)
- 서버 1대에서는 Spring `@Scheduled`로 충분하다. 단, **작업 상태는 DB에 있고 모든 작업은 멱등**이어야 한다 (재시작·중복 실행에 안전).
- 주기 작업은 "시각이 지난 미처리 건"을 조회해 처리하는 방식이다 (예: 노쇼 판정 대상 = `체크인 마감 시각 < now AND 미판정`). 메모리 타이머에 예약하지 않는다.
- 작업 목록: 알림 발송 워커, 노쇼 후보 판정, 이의 기간 경과 확정, 무효 세션 처리, 체크인 오픈 알림, **스터디 종료 처리**(세션 날짜 다음날 00:00), **채팅 메시지 보관 만료 삭제**, 만료된 리프레시 토큰 정리.
- 종료 경계는 **한국 시간 자정**이다. 세션 날짜(KST)를 기준으로 삼고, 비교할 때 `Asia/Seoul` 자정을 UTC 시각으로 바꿔 쓴다. 종료 처리와 삭제는 재실행해도 결과가 같아야 한다.
- 서버를 2대 이상으로 늘릴 때는 분산 락(ShedLock 등)을 도입한다.

### 4.8 채팅 (제안, ADR-0005)
- WebSocket + **STOMP**, 시작은 **단일 서버의 내장(in-memory) 브로커**.
- 메시지는 **먼저 DB에 저장한 뒤** 구독자에게 전달한다. 전달에 실패해도 이전 대화 조회(페이징, 커서 기반)로 복구된다.
- 구독·전송 시마다 **참여 여부(`ACTIVE`)를 서버에서 검사**한다. 나가기 시 해당 사용자의 구독을 끊고 이후 접근을 막는다 (강퇴 기능은 없다).
- **스터디 종료 시 채팅방을 폐쇄**(상태 `CLOSED`, 전체 구독 종료·전송 거부)하고, 메시지는 보관 기간(PRD 4.14, 설정값)이 지나면 스케줄러가 **영구 삭제**한다. 삭제는 한 번에 처리하는 건수에 상한을 둔다.
- 서버 증설 시: Spring의 STOMP 브로커 릴레이는 **RabbitMQ/ActiveMQ 같은 STOMP 브로커**와 연결한다. PRD 4.12의 "Redis pub/sub"은 별도 브리지를 직접 구현해야 하므로, 증설 시점에 **RabbitMQ 릴레이를 우선 검토**한다 (ADR-0005).

### 4.9 정책 설정값 (제안)
- MVP는 `@ConfigurationProperties`(YAML)로 **타입 있는 설정**을 둔다: 체크인 반경, 체크인 시간창, 출석·지각 경계, 취소 기준, 주최자 감점·제재 단계, 최근 N회, 신규 기준 등 (값은 PRD).
- 설정 객체는 그 값을 쓰는 모듈의 `service` 패키지에 `everystudy.<모듈>` 접두사로 둔다(예: 정원 범위와 개설 입력 단위는 `study`, 체크인 반경은 `attendance`). 현재 시각이나 설정값에 따라 달라지는 입력 검사는 서비스가 하고, 실패하면 형식 오류와 같은 `400 VALIDATION_FAILED`로 응답한다(`common/error`의 `InvalidInputException`). 클라이언트가 알아야 하는 값은 `meta` 모듈이 이 객체들을 읽어 `GET /meta/options`로 내려준다. 클라이언트는 수치를 따로 갖지 않는다.
- 코드 곳곳에서 숫자를 직접 쓰지 않고 설정 객체를 주입한다. 운영 중 무배포 변경이 필요해지면 DB 설정 테이블로 옮긴다 (그때 ADR 추가).

## 5. 데이터 설계 원칙 (제안)

- 스키마는 **Flyway만으로** 만든다. 병합된 마이그레이션은 수정하지 않는다 (ADR-0001).
- **시간은 UTC로 저장**하고 표시만 KST로 변환한다. 모든 시간 로직은 주입된 `Clock`을 쓴다 (테스트에서 고정).
- 개인정보(닉네임·이메일·소셜 식별값)는 `user`와 `social_account`에 모은다. 탈퇴 시 이 테이블의 값만 지우고, 다른 테이블은 `user_id`를 그대로 두되 화면에서 "탈퇴한 사용자"로 표시한다 (PRD 4.1 익명화).
- 스터디는 **하루 한 번의 모임**(PRD 4.2)이라 일정은 `study`에 둔다(시작 시각, 진행 시간(분), 장소). 별도 `session`·`schedule_rule` 테이블은 만들지 않는다. 시작한 날 안에 끝나야 한다. 반복 일정은 후속 과제이며, 그때 일정을 별도 테이블로 분리한다(마이그레이션으로 처리).
- 좌표는 위도·경도 컬럼으로 저장한다 (ADR-0001).
- 주요 테이블 후보 (상세는 데이터 명세에서): `user`, `social_account`, `refresh_token`, `study`, `study_target_job`, `study_member`, `study_waiting`, `host_transfer`, `checkin`, `attendance_event`, `user_trust_summary`, `host_penalty_event`, `user_sanction`, `appeal`, `notification_outbox`, `push_subscription`, `notification_setting`, `chat_room`, `chat_message`, `chat_read_state`, `chat_notice`, `report`, `block`, `audit_log`.

## 6. 프론트엔드 구조 (제안)

- Next.js(App Router) + TypeScript, **모바일 우선 반응형**, PWA(웹 푸시용 서비스 워커·manifest).
- 페이지는 PRD 5장의 화면 목록과 1:1로 둔다. 서버 상태 조회는 TanStack Query 한 가지로 통일한다 (ADR-0001 후속 결정).
- API 호출은 한 곳(`frontend/src/lib/api/client.ts`의 `apiFetch`)에서 쿠키 포함(`credentials`)·CSRF 헤더·오류 처리를 담당한다. 화면 코드는 `fetch`를 직접 부르지 않는다. 토큰을 JS로 읽거나 저장하지 않는다.
- 카카오맵은 클라이언트에서만 로드한다 (스터디 만들기: 장소 선택, 상세: 지도 표시). 앱 키는 공개용 JavaScript 키이며 도메인 제한을 건다.
- 패키지 매니저는 **npm**이다 (ADR-0001 후속 결정. CI가 `npm ci` 기준, 도구를 늘리지 않는다).

## 7. 보안과 개인정보

- 시크릿은 환경변수로만 주입하고 저장소에 두지 않는다 (`.env.example`에 키 이름만).
- 모든 상태 변경 API는 **서버에서 권한을 검사**한다 (주최자 본인 스터디만 관리, 채팅방은 참여자만, 어드민은 운영자만).
- 입력 검증은 서버가 최종이다. 위치·시각 같은 판정 입력은 클라이언트를 신뢰하지 않는다.
- 로그에 토큰·이메일·정확한 좌표를 남기지 않는다.
- 위치 정보 수집·이용에 대한 **개인정보 처리방침**은 출시 전에 준비한다 (PRD 8장).

## 8. 테스트 전략

### 8.1 원칙: 피라미드 모양, 통합 테스트는 필요한 곳에만

- 테스트는 **단위 테스트가 대다수**인 피라미드 모양으로 둔다. 개수 비율은 목표(단위·슬라이스가 대략 70~80%)이지 강제 규칙이 아니다. 숫자를 맞추려고 의미 없는 테스트를 늘리지 않는다.
- **통합 테스트는 "DB·트랜잭션·보안 설정의 동작 자체"를 검증할 때만** 쓴다. 정원 동시성, 락, 유니크 제약, 마이그레이션, 스케줄러 조회 쿼리는 실제 DB 없이 검증할 수 없으므로 통합 테스트가 필수다. 비즈니스 규칙(판정·점수·승계 규칙)은 단위 테스트로 검증한다.
- **테스트를 가능한 한 아래 층으로 내린다.** 상위 테스트가 실패했는데 하위 테스트가 실패하지 않았다면 하위 테스트를 추가하고, 하위에서 이미 검증한 것을 상위에서 반복하지 않는다.
- 실행을 나눈다: `test`(단위·슬라이스, 빠름)와 `integrationTest`(Testcontainers). 통합 테스트에는 태그를 붙여 CI에서 개수를 볼 수 있게 한다. Testcontainers MySQL 컨테이너는 테스트 JVM 하나에서 공유한다.

### 8.2 무엇을 어떻게 검증하나

| 대상 | 종류 | 방법 |
|---|---|---|
| 정원·승계 규칙, 출석 판정·점수 | 단위 | 순수 클래스·함수. 고정 `Clock`·`RandomSource`로 PRD 4.6~4.13의 시간 경계값을 매개변수 테스트 |
| 종료·삭제 | 단위 + 통합 | 규칙(자정 KST 경계)은 단위, 재실행 안전성(멱등)과 조회 조건은 통합 |
| 정원·승계 동시성 | 통합 | Testcontainers MySQL로 다중 스레드 신청 (마지막 1자리, 주최자·참여자 동시 나가기) |
| 마이그레이션 | 통합 | Testcontainers에 실제 Flyway 적용 후 JPA `validate` |
| 컨트롤러 입력 검증·오류 응답 | 슬라이스 | `@WebMvcTest` 등 웹 계층만 로드 |
| 인증·CSRF | 통합 | 쿠키 속성, CSRF 누락 시 거부, 만료·회전 |
| 모듈 경계 | 구조 | 아키텍처 테스트(ArchUnit)로 금지된 의존 검출. 위반 예시 패키지로 규칙이 실제로 실패하는지도 확인한다 (3장) |
| 프론트 | 단위·컴포넌트 | Vitest + Testing Library. E2E(Playwright)는 후속 |

### 8.3 의존 역전(DIP)은 경계가 있는 곳에만

테스트를 쉽게 하려고 모든 계층에 인터페이스를 두지 않는다 (ADR-0003: 모듈형 모놀리스). 아래 **느리거나 외부에 의존하는 경계**에만 인터페이스를 두고 테스트에서는 가짜 구현을 쓴다.

| 경계 | 방식 |
|---|---|
| 시간 | 주입되는 `Clock` (4.9) |
| 무작위(승계 추첨) | 주입되는 `RandomSource` (4.3) |
| 알림 채널(웹 푸시, 이메일), 소셜 로그인 공급자 | 인터페이스 + 가짜 구현 |
| 정책 계산(판정, 점수, 거리) | DB·Spring·시간에 의존하지 않는 순수 클래스·함수. 입력을 받아 결과만 돌려준다 |
| Repository | Spring Data 인터페이스를 그대로 쓴다. 쿼리는 통합 테스트로 검증하고, 서비스 단위 테스트가 꼭 필요할 때만 가짜를 쓴다 |

### 8.4 작성 규칙

- 실패하는 테스트를 먼저 쓰고(TDD), 최소 구현으로 통과시킨 뒤 정리한다. 규칙 하나에 테스트 하나, 경계값은 매개변수 테스트로 둔다.
- 구현이 아니라 **행동**을 검증한다. 깊은 Mockito 스텁보다 직접 만든 가짜를 우선한다.
- 테스트 데이터는 빌더로 만든다 (엔티티 생성 방식이 바뀌어도 한 곳만 고친다).
- 테스트에 실제 토큰·개인정보를 쓰지 않는다 (AGENTS.md 5장).

## 9. 배포와 환경 (Docker 확정, 호스팅 업체는 미정)

- 로컬: Docker Compose (MySQL). 소규모 확정이므로 Redis는 두지 않는다.
- 운영: **VM 1대 + Docker Compose** (백엔드, 프론트, 역프록시·TLS, MySQL 또는 관리형 DB). 컨테이너는 `restart: unless-stopped`로 장애 후 자동으로 다시 켠다. 호스팅 업체와 도메인은 **미결정**이다 (비용 확인 후).
- 프론트와 백엔드는 같은 사이트(예: `app.<도메인>`, `api.<도메인>`)로 두어 쿠키 인증을 단순하게 유지한다.
- 환경: `local`, `prod` (스테이징은 필요해질 때). `prod`는 Spring 프로파일(`SPRING_PROFILES_ACTIVE=prod`)로 켜고, 개발용 도구인 API 문서와 Swagger UI는 `prod`에서 끈다. DB 백업과 복구 절차는 배포 확정 시 정한다.
